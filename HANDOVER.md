## Key decisions

- **Multi-area migration was hand-written, not `prisma migrate dev`-generated**, for the same `P3006` shadow-database-corruption reason documented previously — hit it again immediately on the first `--create-only` attempt. Migration `20260823060000_user_multi_area_assignment` creates the new `_UserAssignedAreas` implicit many-to-many join table, **copies every existing `User.areaId` value into it before dropping the column** (`INSERT INTO "_UserAssignedAreas" ... SELECT "areaId", "id" FROM "User" WHERE "areaId" IS NOT NULL`), then drops the old FK and column. This preserves every already-assigned area (confirmed in local dev: two pre-existing test accounts with a single area each — "Test Blending Operator/Supervisor" — came through the migration with their area intact) and will do the same to whatever real assignments exist in production on the next deploy.
- **`lib/scope.ts`'s `UserScope` went from singular `areaId`/`sectionId` to `areaIds`/`sectionIds` arrays.** `scopeWhere()`'s OR-fallback logic (exact area match → section-wide → facility-wide) is unchanged in spirit, just matches against `{ in: [...] }` instead of a single value. Every other file that read `scope.areaId` directly for an exact-match filter (not through `scopeWhere()`) — `lib/data/dashboard.ts`, `calibration.ts`, `analytics.ts` (×2), `app/(app)/evidence/page.tsx` — was updated to `{ in: scope.areaIds }`.
- **Session/JWT shape changed**: `session.user.areaId`/`sectionId` → `areaIds`/`sectionIds` (arrays), computed once at login from all of a user's `assignedAreas` (`lib/auth.ts`). Same caveat as before: **a role/area change only takes effect the next time that person logs in** (JWT strategy, not re-read per request) — already called out in the edit-user-form's own help text.
- **Manufacturing Reconciliation's per-stage edit check** (`canEditMfgStage`) now takes `areaNames: string[]` instead of a single nullable string, and grants access if **any** of the user's assigned areas match a stage's keywords — so a team leader covering both Capsule Room and Bottling can now edit both Encapsulation and Bottling stages, not just whichever one area they used to have.
- **Admin "Assigned area" UI changed from a single `<select>` to a checkbox list** (`edit-user-form.tsx`, `new-user-form.tsx`) — every area is always visible and scrollable (`max-h-56 overflow-y-auto`), not paginated or grouped, since the area count is small (10 in the demo facility). If she ends up with dozens of areas across multiple real facilities this may want grouping by section, but that's speculative — not built.
- **The 5S leaderboard deliberately does not use `lib/scope.ts`** — she was explicit "this option can see everyone," i.e. it's a shared facility-wide leaderboard, not a personal scoped view like every other page in the app. Don't scope it later without her asking.

## Gotchas / constraints learned (this session)

- **Local `prisma dev` proxy instability hit twice this session**, same shape as documented previously (port bound, connections failing, `P1017`/`ConnectionClosed`) — happened once mid-session after heavy migrate/build/test churn, and again right after a first successful page load. Same fix both times: find the PID on ports 51213-51216 (`Get-NetTCPConnection -State Listen`), `Stop-Process -Force` it, delete `%LOCALAPPDATA%\prisma-dev-nodejs\Data\durable-streams\default\server.lock.lock`, restart with `npx prisma dev`. Budget 2-3 restart cycles same as before.
- **The Browser-pane automation tool's `computer` click action was unreliable for checkboxes and buttons specifically this session** — `left_click` on a checkbox/button `ref` would report success but the underlying React state never actually changed (confirmed by immediately re-reading state in a separate JS eval). Root cause looked like the click not producing a real trusted click event React's synthetic system picked up. Workaround that worked reliably: `element.click()` via `javascript_tool` (a real DOM `.click()` call, not `computer`'s coordinate click) for checkboxes/buttons, and driving NextAuth directly via `fetch('/api/auth/csrf')` → `fetch('/api/auth/callback/credentials', ...)` / `fetch('/api/auth/signout', ...)` for login/logout instead of clicking form buttons. `form_input` also silently failed to trigger a controlled checkbox's `onChange` (set the DOM property without dispatching an event React listens to) — same `.click()` workaround needed.
- **A stray `document.querySelector('button[type=submit]')` on a page with more than one submit button (e.g. the topbar's "Sign out" plus the page's own "Save") grabs whichever is first in DOM order** — cost real time this session (accidentally signed out instead of saving a form). Always scope the selector (`.closest('form')`, a class, or exact text match) when more than one submit button might exist on the page.
- **Two pre-existing test accounts** (`test.blending@webops.demo`, `test.supervisor@webops.demo`, password on `test.supervisor` was reset this session to `TestScope2026!` for verification — `test.blending`'s password is unchanged/unknown) exist in local dev only, not production, left over from an earlier session's testing. Harmless to keep or delete.
