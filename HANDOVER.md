## Gotchas / constraints learned this session

- **`prisma migrate dev` fails locally** with `type "UserRole" already exists` (shadow DB stuck in a bad state) — hit this on both migrations created this session. Workaround, not a real bug: `npx prisma db push` (applies straight to the real dev DB) → hand-write `migration.sql` from the schema diff → `npx prisma migrate resolve --applied <name>`. Don't waste time trying to repair the shadow DB itself.
- **`prisma migrate deploy` *hangs* (doesn't error, just never returns) against Neon's pooled connection string.** Root cause and fix already shipped in commit `f2924de`: `prisma.config.ts`'s migration `datasource.url` must read `DATABASE_URL_UNPOOLED`, not `DATABASE_URL`. If Neon is ever reconnected/reprovisioned for this or another Vercel project, re-check this wiring first before assuming something else broke.
- **A stray local `.env` value can leak into `vercel deploy`.** The CLI's own warning ("Detected .env file, it is strongly recommended to use Vercel's env handling instead") is not idle — a leftover `NEXTAUTH_URL=http://localhost:3017` caused production login to redirect to localhost after successful auth. Fixed by deleting that line (the app doesn't need it: `trustHost: true` in `lib/auth.config.ts` derives the right URL from request headers in every environment) and adding `.vercelignore` excluding `.env*`.
- **`vercel env pull` / `vercel link` / `vercel blob create-store` etc. write `.env.local` in this directory, which Next.js loads with *higher priority* than `.env`.** This silently broke local dev login (`AUTH_SECRET` mismatch → "no matching decryption secret" JWT errors) right after a round of production provisioning commands. Delete `.env.local` after any Vercel CLI session here — don't leave it lying around, and check for it first if local dev suddenly can't decode sessions or hits stale-user foreign-key errors for no obvious reason.
- **Browser console message history seems to accumulate rather than reset** — `read_console_messages` returned what looked like a fresh error but was actually identical (same digest, same stale ID) to something from much earlier in the session. When a "reproduction" looks suspiciously identical to an old error, check fresh server-side logs instead of trusting the console buffer's apparent freshness.
- **Unresolved**: the user saw `Minified React error #441` in production after rapidly ticking ~34 checkboxes then hitting Submit. Not reproduced locally after a clean reseed + fresh login (34 rapid clicks all returned clean 200s). `react.dev/errors/441` 404s — the code isn't in the public catalog for whatever React/Next version is in play, so its meaning is still unknown.
