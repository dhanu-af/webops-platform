## Key decisions

- **Real controlled documents are built via the live admin UI (Checklist Builder → Workflow Builder → Schedule Manager), never via `prisma/seed.ts` + reseed.** Reseeding production wipes data and is a standing, still-undecided, separate question (see Open Questions) — building content live sidesteps it entirely and is immediately usable. This is *the* pattern for adding any future real checklist content.
- **Checklist versioning is real and load-bearing**: every edit to a checklist's items publishes a new version; historical inspections keep the exact version they were performed against. This is why the user's already-submitted 5S Daily Check inspection from today still shows the old numeric-spinner UI even after the checklist itself was changed to Yes/No/N/A and then to tap-buttons — that's correct behavior, not a bug, and should never be "fixed" by editing in place.
- **Feedback on the 5S scoring UI went through two rounds — the second, more specific round is the one that stuck.** Round 1 ("please mention numbering system" screenshot showing a bare number spinner) was answered by converting to Yes/No/N/A — this was an *overcorrection* that dropped the paper form's real middle "Needs improvement" level. Round 2 ("add number as click system 0 1 2") clarified she wanted the **real 0/1/2 scale kept**, just as tap buttons instead of typing. Final, current state: `NumericScaleButtons` component (`components/inspection/checklist-item-card.tsx`) — any `NUMERIC` item with a bounded range ≤10 renders one button per value (colored critical→warn→pass by position), wider ranges (temperature, humidity) keep the free-text input. **Lesson for next time**: when feedback is about *input friction*, the fix is usually a better input widget, not fewer choices.
- **Single-step "Supervisor Check" workflow** was added (no separate Operator step) specifically because 5S-style checks are performed and signed off by the reviewer themself. Matches existing precedent in this app (see `prisma/seed.ts`'s Capsule Room comment: QA does spot-checks, not per-form sign-off).
- **Checklist cloning copies items but never schedules.** A clone is almost always for a different area than the source; carrying over the source's schedule would just create a duplicate pointing at the same place. This is *why* new clones always start at "0 schedules" and need one added manually — expected, not a bug (see Next steps #1, this confused the user today).
- **Timezone correctness (major thread today)**: Vercel functions run in UTC; this facility is in Queensland (`Australia/Brisbane`, UTC+10, no DST). Every "what day is it" computation across the app used to silently mean the *server's* day, not the *facility's* — for roughly the first 10–14 hours of every real Brisbane day, Today's Ops / the Dashboard / the Calendar could have been showing yesterday's picture. Fixed via a new `lib/timezone.ts` (see Files touched) and applied everywhere date boundaries or displayed timestamps mattered. **This was a real, user-caught bug** ("the topbar says Friday 21 August, my clock already says the 22nd"), not cosmetic.
- **Server-rendered timestamps vs. client-rendered ones are a different bug with a different fix.** `formatAttribution()` (the "Jordan Blake — 19 Aug, 14:32" line under checklist items) runs in `"use client"` components and reads the *viewer's own browser clock* — already correct for a real user physically in Queensland, deliberately left alone. Only *server*-rendered `format()` calls (Audit Trail, Reports, Evidence Gallery, Inspection History, checklist version history) needed fixing, since those bake the server's UTC time into the HTML regardless of who's viewing it.
- **A GitHub multi-account gotcha, confirmed again today**: pushing needs `gh auth switch --hostname github.com --user dhanu-af` first, then switch back to `khdanushka-spec` afterward (the default for her other projects). Every single push this session followed this exact two-command bracket.
- **Push confirmation pattern this session**: after each feature, ask "want this pushed?" before running `git push`, even though `git commit` locally doesn't need to ask. The one time this was skipped (auto-pushing after "next" with no explicit "push" in the same turn) was noted as a one-off deviation, not a new standing permission — go back to asking each time by default.

## Gotchas / constraints learned this session

- **Local Postgres (`npx prisma dev`) stops between sessions/long gaps — check `netstat -ano | grep 51214` before assuming a code problem.** Happened at least three times today. Fix: `npx prisma dev` from the repo root, comes back on the same port.
- **A concurrent Claude Code session sharing this same `~/webops-platform` directory** was running its own `next dev` (port 3017) most of today. Its in-memory Prisma Client is now **several migrations/schema-generations behind** and will need `taskkill` + `rm -rf .next` + restart before it can touch anything that changed today. Never killed it — always verified changes in an isolated `git worktree` instead (see below).
- **The reliable verification recipe used all session**: `git worktree add ../webops-platform-verify HEAD`, copy `.env`, `ln -s` the real `node_modules` (this can silently take >90s and get moved to background — that's normal, not a hang), `node ../webops-platform/node_modules/prisma/build/index.js generate`, then run `next dev` via `node ../webops-platform/node_modules/next/dist/bin/next dev --port 3019` directly (plain `npx next dev` inside a worktree sometimes fails to resolve symlinked `node_modules` correctly). Always `git worktree remove --force` + `rm -rf` the directory afterward — it can report "device or resource busy" immediately after the process exits, just retry once.
- **The Checklist Builder's item editor has a real, reproducible React state bug under Turbopack dev HMR**: editing many items in one long unsaved session can cause edits past a certain point to silently not persist (confirmed via direct DB queries — not a false alarm). Most likely Fast Refresh partially remounting the component and corrupting the array-index-keyed item list. **Fix that actually worked**: publish incrementally in smaller batches (~14 items, publish, reload, repeat) rather than one long unsaved edit session. Did not reproduce on production (static build, no HMR).
- **`db.facility.findFirst()` with no filter is unsafe** — this repo has an archived leftover test facility ("Second Site Test") alongside the real one, and Postgres gives no ordering guarantee without `orderBy`. A one-off verification script using unfiltered `findFirst()` silently updated the *wrong* facility row today, leaving the real one's timezone stuck on a test value (`America/New_York`) for a while during verification. Always filter `archived: false` (matching `getFacilityTimezone()`'s own convention) or query by explicit id.
- **Browser automation click reliability**: `computer` tool's `left_click` on a `ref` intermittently doesn't fire the handler; `element.click()` via `javascript_tool` is reliable. For React controlled `<input>`/`<select>` values set via script, use the native prototype setter + dispatch both `input` and `change` events (documented pattern, used throughout today's verification scripts).
- **GitHub two-account switch is required before every push**: `gh auth switch --hostname github.com --user dhanu-af`, push, then `gh auth switch --hostname github.com --user khdanushka-spec` back.
