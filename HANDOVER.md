### New "Manufacturing Reconciliation" module

An 8-stage GMP-style batch traceability & reconciliation record: **Warehouse Issue → Blending → Encapsulation → Bottling → X-Ray/Metal Detection → Packaging → Finished Goods Warehouse → Dispatch**. One `MfgBatch` has up to 7 one-to-one sub-stage records (each independently optional/startable) plus a one-to-many `MfgDispatchEvent` log (a batch can ship in parts).

**Adapted, not copied, to this project's own conventions**:
- **Schema**: real `createdBy User @relation` on `MfgBatch` only (matching this project's `EquipmentCalibration`/`CapsuleCalculation` convention). Every per-stage "who did this" field (`issuedByName`, `blendedByName`, `completedByName`, `checkedByName`, `inspectedByName`, `packedByName`, `qaReleasedByName`, `dispatchedByName`) stayed a **plain string, deliberately not a User relation** — these mirror real paper GMP form signature fields, which record whoever physically performed that step and may not have (or need) a WebOps login; who actually *saved* each stage in the system is already captured per-edit in `AuditLog`. This is a considered adaptation, not an oversight.
- **No Formulation/BOM link**: the reference links `MfgBatch` to a `BatchRecord` model this project has no equivalent of. Replaced with a plain optional `formulationReference String?` free-text field. The reference's "auto-populate Warehouse Issue raw materials from the linked Batch Record" feature was dropped entirely (nothing to auto-populate from) — raw material lines are added by hand; the standard packaging material lines still auto-pre-populate on batch creation (that part didn't depend on the missing module).
- **Permission**: added a new `"mfg.manage"` permission to `lib/permissions.ts` (granted to `SUPER_ADMIN`, `ADMIN`, `SUPERVISOR`, `QA`, `MANAGEMENT`) — this is a genuinely new capability domain, not equivalent to any existing permission's role set (`reports.view` is read-only/analytics, `calibration.manage` is a different domain and missing `SUPERVISOR`), so a new permission follows this app's own established "one permission per manageable domain" pattern rather than being scope creep. **Viewing the module has no permission gate at all** (matches the reference's own permissive read model, same as Inspections) — any authenticated user can view the list/dashboard/batch detail/download the PDF; only create/save/delete/mark-completed/dispatch actions require `mfg.manage`. UI hides write affordances (New Batch, stage Save buttons, Mark Completed, Delete) when the viewer lacks it, inputs render `disabled` rather than removed.
- **PDF export uses `@react-pdf/renderer`, not `pdfkit`** — this project already has a PDF report (`lib/pdf/report-document.tsx`) built with react-pdf; introducing a second PDF library for one feature would've been an unnecessary dependency. Rebuilt the pdfkit version's exact document structure (title block, per-stage bordered label:value rows, material line tables, the Final Reconciliation table with PASS/FAIL coloring, page-N-of-M footer) using react-pdf's View/Text/StyleSheet flexbox model instead of pdfkit's imperative `doc.rect()`/`doc.text()` calls — considerably simpler, since react-pdf paginates automatically (no manual `ensureSpace`/`addPage` bookkeeping needed).
- **Final Reconciliation is its own 9th tab**, not an always-visible section below the stage tabs like the reference — matching her literal spec ("a tab per stage plus a Final Reconciliation summary tab").

## Key decisions

- **Never enter a password to log into anything on the user's behalf, even for her own site.** Hard rule.
- **"Section" in her vocabulary usually means the app's `Area` model**, not its actual `Section` model. Reading-comprehension note, not a code gap.
- **`npm run build` is plain `next build`**; `npm run vercel-build` (`prisma migrate deploy && next build`) only runs on Vercel and will auto-apply any pending migration the moment this gets pushed and deployed — no manual production migration step needed or attempted.
- **GitHub push requires an account switch**: `gh auth switch --hostname github.com --user dhanu-af`, push, then switch back to `khdanushka-spec`.
- **Always ask before `git push`, never before local `git commit`.**
- **`prisma migrate reset`/`--force` gets refused by Prisma's own CLI when it detects an AI agent, unless the user's exact consenting message is passed through an env var.** Don't reach for it to fix a corrupted local shadow database (`P3006`) — hand-write the migration SQL (copy an existing migration file's style) and apply with `prisma migrate deploy`, which never touches the shadow DB. Worked cleanly for this session's migration on the first attempt.
- **A file is only safe to import from a `"use client"` component if nothing in its import chain touches `lib/db` at module scope** — this is why `lib/mfg-reconciliation.ts` (pure math, imported by client-side stage sections) has zero DB import, while `lib/data/mfg-reconciliation.ts` and `lib/actions/mfg-reconciliation.ts` (both DB-touching) are only ever imported from Server Components or as `"use server"` actions.
- **A plain (non-`"use server"`) function in `lib/data/*.ts` cannot be called directly from a `"use client"` component**, even via `useEffect` — it needs the DB connection, which isn't available client-side. Caught this while wiring the batch detail page's audit trail: fixed by fetching it server-side in `page.tsx` and passing the result down as a prop, rather than fetching client-side on mount. Cheaper anyway (one less round-trip).
- **When a new feature is a genuinely new capability domain** (not equivalent in spirit to any existing permission's role set), adding a new permission entry to `lib/permissions.ts` is the *correct* move, following this app's own established pattern of one permission per domain — not scope creep. Contrast with the Calculation module, which reused `reports.view` because it genuinely was the same kind of capability (a planning tool for the same manager-tier roles).
- **When a reference implementation from another of her projects models a "who did this" field as a real user-account relation, check whether it actually represents a system action (make it a relation) or a real-world/paper-record attribution that may not correspond to any system user (keep it a string).** Encapsulation's "Checked By" is a QA sign-off name for a physical GMP form, not necessarily whoever clicked Save in WebOps — got this right by reasoning about the field's real-world meaning, not just copying the reference's own choice.

## Gotchas / constraints learned

- **Local `prisma dev` proxy instability recurred multiple times again this session**, in two distinct failure modes: (1) `P1017`/"Connection terminated unexpectedly" mid-request — transient, sometimes clears after a plain restart of just `prisma dev`; (2) the proxy process reports itself already running and bound to its ports (confirmed via `Get-NetTCPConnection -State Listen`) yet every real connection attempt still fails outright — this one needs killing the actual owning PID (`Get-NetTCPConnection -LocalPort 51214 -State Listen | select OwningProcess`) before a fresh `npx prisma dev` will bind cleanly, and sometimes *also* needs the stale-lock-file removal (`%LOCALAPPDATA%\prisma-dev-nodejs\Data\durable-streams\default\server.lock.lock`) on top of that. Budget for 2-3 restart cycles combining both fixes before it's reliably useable; this is environment flakiness, not a sign anything you built is wrong — a real bug you introduced looks different (a specific query/route failing consistently across restarts, not everything failing identically for a few minutes).
- **Reliable page-level verification recipe without the Browser tool**: `npm run dev` in the background, then NextAuth via curl (`GET /api/auth/csrf` → `POST /api/auth/callback/credentials` with `csrfToken`/`email`/`password`/`callbackUrl`/`json=true`, cookies via `-c`/`-b`). Demo accounts all share password `WebOps2026!` (`admin@webops.demo` = SUPER_ADMIN, `jordan.operator@webops.demo` = OPERATOR, others in `prisma/seed.ts`). For anything needing real seeded data beyond what's in `prisma/seed.ts`, a throwaway `tsx` script (with `import "dotenv/config"` at the top — `tsx` doesn't auto-load `.env`) hitting `lib/db.ts` directly works well for setup and teardown; delete the script before committing.
- **For a PDF route, `pdftotext` (from poppler-utils, available as `/mingw64/bin/pdftotext` in this Git Bash environment) extracts real text content for verification** — far more useful than just checking the response is "a PDF" (`file <name>.pdf`, which only confirms valid PDF *format*, not correct *content*). Used this to confirm the reconciliation math in the exported PDF actually matches expectations, not just that a PDF came back.
