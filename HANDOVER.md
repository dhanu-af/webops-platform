## Investigation: "Minified React error #441"

**MITIGATED, not fully root-caused — correcting an earlier wrong conclusion in this same doc.** An earlier pass through this session concluded the bug was isolated to specific old, "contaminated" inspection records and deleting them would fix it. That was wrong: after wiping **every** inspection on production and creating genuinely brand-new ones, the error still recurred (twice, with two different digests: `3785944413` and `2375333021`) on records that had never existed before the wipe. What actually distinguishes failures from successes across ~6 attempts this session isn't the record's age, the submitting user's role, or anything else that could be pinned down by inspection or local reproduction — locally, every single attempt succeeded (multiple users, multiple checklist types, both batch and paced click patterns), while production failed intermittently regardless of who or what. That pattern points to a transient infrastructure issue (most likely Neon connection flakiness under the burst of sequential DB writes `submitInspection` performs) rather than a deterministic application bug — but this is still a reasoned inference, not a confirmed root cause, since no one has actually seen the real error behind either digest (no Vercel log/CLI access this session).

**Fix shipped (commit `84c3969`)**: two defensive changes that should absorb this class of transient failure without needing to know the exact failing line:
1. `submitInspection`'s reviewer-notification loop is now wrapped in a per-reviewer `try/catch` — a failed notification (best-effort, non-critical) can no longer fail the whole submission.
2. `SubmitBar` now retries `submitInspection` once, silently, before showing an error to the user. This is safe specifically because of a confirmed fact: when the error appeared, the inspection's status had **not** actually changed in the database (verified by reloading the failed record) — so nothing has been written yet at the point of failure, and a retry can't cause any duplicate-write side effects.

**If this recurs even after the retry** (i.e. two consecutive attempts both fail), that's a much stronger signal of a real, deterministic bug rather than transient flakiness — worth escalating to actual Vercel function log access at that point rather than continuing to reason from the client side.

## Gotchas / constraints learned across sessions

- **`prisma migrate dev` fails locally** with `type "UserRole" already exists` (shadow DB stuck). Workaround: `npx prisma db push` → hand-write `migration.sql` from the schema diff → `npx prisma migrate resolve --applied <name>`.
- **`prisma migrate deploy` hangs against Neon's pooled connection string.** Fix (already shipped, `f2924de`): `prisma.config.ts`'s migration `datasource.url` must read `DATABASE_URL_UNPOOLED`, not `DATABASE_URL`.
- **A stray local `.env` value can leak into `vercel deploy`.** Keep `.env*` out via `.vercelignore`; the app doesn't need `NEXTAUTH_URL` since `trustHost: true` in `lib/auth.config.ts` derives it from request headers.
- **`vercel env pull` / `vercel link` / `vercel blob create-store` write `.env.local`, which Next.js loads with *higher priority* than `.env`.** Delete `.env.local` after any Vercel CLI session here, or local dev login breaks with "no matching decryption secret" / stale-user FK errors.
- **Never run standalone one-off scripts (`npx tsx some-script.ts`) against the local `npx prisma dev` Postgres without an explicit, awaited `db.$disconnect()` before `process.exit()`.** It's PGlite under the hood (check `AppData/Local/prisma-dev-nodejs/Data/durable-streams/<name>/`), not a real `postgres.exe`, and abrupt exits leave connections open server-side. Doing this 3-4 times in one session exhausted its connection limit, breaking the *actual* dev server's login and every DB-backed page too — required 3 rounds of restarts (Next dev, then `npx prisma dev` itself, then Next dev again) to recover. Trivial to avoid, expensive to unwind.
- **Force-killing (`taskkill /F`) the local `npx prisma dev` process can leave a stale lock directory behind**: `AppData/Local/prisma-dev-nodejs/Data/durable-streams/<name>/server.lock.lock`. Next start then fails with "Lock file is already being held" or silently claims "already running" against a half-dead server. Delete that directory first if a restart won't come up clean.
- **`npm run dev` / `next dev` binds port 3000 unless the port is passed explicitly.** `.claude/launch.json`'s port mapping (3017) is only honored by the `preview_start` tool, not plain `npm run dev` via Bash — use `PORT=3017 npm run dev` when starting by hand.
- **`TaskStop` on a `npm run dev` background task doesn't reliably kill the actual `next-server` process** — only the `npm` wrapper. Verify with `netstat -ano | grep <port>` after, and `taskkill //PID <pid> //F` the real PID if it's still listening.
- **This machine has multiple Neon Postgres projects under the same `DKNS`/`dkns1` Vercel team** (`neon-byzantium-saddle` = webops-platform's real DB; `neon-coral-bucket` = an unrelated project with `add_about_video`/`sales_orders`-style migrations, likely one of the user's other apps). Neon's own project switcher doesn't default to the right one — always get to Neon via the specific Vercel project's **Storage** tab, never Neon's own top-level project list, or you'll query the wrong DB and get real-but-misleading results (cost a full round of back-and-forth this session).
- **Neon's SQL Editor is a genuinely reliable fallback for inspecting production DB state with zero Vercel CLI/token setup** — default to it for read-only verification over chasing CLI auth.
- **2026-08-20: local dev server hit a persistent Turbopack panic** — `FATAL: An unexpected Turbopack error occurred`, failing to compile `app/globals.css` via PostCSS, child process exiting with Windows code `0xc0000142` (`STATUS_DLL_INIT_FAILED`). Happened after a long session of repeated process kills/restarts (Next dev server × 3, `npx prisma dev` × 2) on a machine already running ~14 node processes for other projects. Restarting the dev server alone did **not** fix it — same panic every time. **Fix that worked: `rm -rf .next` then restart.** The Turbopack build cache had gotten corrupted from all the abrupt kills; a full delete-and-rebuild resolved it immediately, and also fixed the previously-unexplained `/inspections/[id]` hard-nav-404 bug from an earlier session — that was Turbopack cache corruption too, not an application bug. If Turbopack panics again on any route, try this before anything more invasive.
- **Force-killing processes got blocked once by the Claude Code auto-mode permission classifier** after several kills earlier in the same session ("Blocked by classifier" — reasonable given how many restarts had already happened), then allowed again on retry a few minutes later. Not a hard ban — but a sign to slow down and consider asking the user rather than mechanically retrying.
- **Multiple concurrent Claude Code sessions can end up in the same `~/webops-platform` directory** sharing the same dev server and local Postgres — check `tasklist`/`netstat` for existing owners before assuming exclusive control, and coordinate before restarting shared local infrastructure.
