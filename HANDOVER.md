## Gotchas / constraints learned this session

- **`prisma migrate dev` fails locally** with `type "UserRole" already exists` (shadow DB stuck in a bad state) — hit this on both migrations created this session. Workaround, not a real bug: `npx prisma db push` (applies straight to the real dev DB) → hand-write `migration.sql` from the schema diff → `npx prisma migrate resolve --applied <name>`. Don't waste time trying to repair the shadow DB itself.
- **`prisma migrate deploy` *hangs* (doesn't error, just never returns) against Neon's pooled connection string.** Root cause and fix already shipped in commit `f2924de`: `prisma.config.ts`'s migration `datasource.url` must read `DATABASE_URL_UNPOOLED`, not `DATABASE_URL`. If Neon is ever reconnected/reprovisioned for this or another Vercel project, re-check this wiring first before assuming something else broke.
- **A stray local `.env` value can leak into `vercel deploy`.** The CLI's own warning ("Detected .env file, it is strongly recommended to use Vercel's env handling instead") is not idle — a leftover `NEXTAUTH_URL=http://localhost:3017` caused production login to redirect to localhost after successful auth. Fixed by deleting that line (the app doesn't need it: `trustHost: true` in `lib/auth.config.ts` derives the right URL from request headers in every environment) and adding `.vercelignore` excluding `.env*`.
- **`vercel env pull` / `vercel link` / `vercel blob create-store` etc. write `.env.local` in this directory, which Next.js loads with *higher priority* than `.env`.** This silently broke local dev login (`AUTH_SECRET` mismatch → "no matching decryption secret" JWT errors) right after a round of production provisioning commands. Delete `.env.local` after any Vercel CLI session here — don't leave it lying around, and check for it first if local dev suddenly can't decode sessions or hits stale-user foreign-key errors for no obvious reason.
- **Browser console message history seems to accumulate rather than reset** — `read_console_messages` returned what looked like a fresh error but was actually identical (same digest, same stale ID) to something from much earlier in the session. When a "reproduction" looks suspiciously identical to an old error, check fresh server-side logs instead of trusting the console buffer's apparent freshness.

Not reproduced locally after a clean reseed + fresh login (34 rapid clicks all returned clean 200s). `react.dev/errors/441` 404s — the code isn't in the public catalog for whatever React/Next version is in play, so its meaning is still unknown. - **This session ran concurrently with another Claude Code session in the same `~/webops-platform` directory** — discovered because attempting `npm run dev` on port 3017 failed with "Another next dev server is already running... PID 9632", and a harness hook explicitly flagged "Another chat's dev server is running in this folder." Reused that existing server via direct browser navigation rather than starting a second one. If you're picking this up fresh: check whether that other session/dev server is still active before restarting anything, clearing `.next`, or touching shared local Postgres (`npx prisma dev`, ports 51213-51215) — coordinate rather than assuming exclusive ownership of this working directory.
- **Never run standalone one-off scripts (`npx tsx some-script.ts`) against the local `npx prisma dev` Postgres without an explicit, awaited `db.$disconnect()` before `process.exit()`.** Abrupt process exit leaves the connection open server-side; do this a few times (I did it 3-4 times debugging the FK/404 issue) and the embedded Postgres (it's PGlite under the hood, not a real `postgres.exe` — check `AppData/Local/prisma-dev-nodejs/Data/durable-streams/<name>/`) runs out of connections and starts closing new ones with a generic "Server has closed the connection" / "Connection terminated unexpectedly", which then breaks the actual dev server's login and every DB-backed page too. This cascaded into needing 3 rounds of restarts (Next dev server, then `npx prisma dev` itself, then Next dev server again) before things were stable — expensive to unwind, trivial to avoid.
- **Force-killing (`taskkill /F`) the local `npx prisma dev` process can leave a stale lock directory behind**: `AppData/Local/prisma-dev-nodejs/Data/durable-streams/<name>/server.lock.lock`. The next `npx prisma dev` start then fails with "Lock file is already being held" (or worse, silently reports "already running" against a half-dead server). If restarting it, and it won't come up clean, check for and delete that `server.lock.lock` directory first.
- **`npm run dev` / `next dev` here always binds port 3000 unless you pass the port explicitly** — `.claude/launch.json` records port 3017 for this project, but that mapping is only honored by the `preview_start` tool, not by running `npm run dev` directly via Bash. Use `PORT=3017 npm run dev` (or `next dev -p 3017`) when starting it by hand, otherwise you'll get a silent mismatch and confuse yourself thinking the server isn't up.
- **`TaskStop` on a `npm run dev` background task does not reliably kill the actual `next-server` process** — it seems to only stop the `npm` wrapper, leaving the real Node process (and its port) still alive. Confirmed twice this session. If a restart is needed, verify with `netstat -ano | grep <port>` afterward and `taskkill //PID <pid> //F` the actual PID if it's still listening.
- **This machine has multiple Neon Postgres projects under the same `DKNS`/`dkns1` Vercel team** (at minimum `neon-byzantium-saddle` = webops-platform's real DB, `neon-coral-bucket` = some unrelated project with `add_about_video`/`sales_orders`-style migrations). Neon's own project switcher doesn't default to "the one you want" — if the user opens Neon's SQL Editor directly rather than going through the `webops-platform` Vercel project's **Storage** tab, they can easily end up querying the wrong database and get misleading (but real-looking) results. Confirmed this cost a full round of back-and-forth this session: a `_prisma_migrations` check against the wrong DB looked like the migration hadn't applied, when it actually had. Always get to Neon via the specific Vercel project's Storage tab, not Neon's own project list.
- **Neon's SQL Editor is a genuinely reliable fallback for checking/inspecting production DB state when no working Vercel CLI token is available** — no token, no `vercel env pull`, just read-only SQL. Worth defaulting to this over chasing CLI auth issues, for read-only verification at least.
